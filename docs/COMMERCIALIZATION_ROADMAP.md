# نقشهٔ راه تبدیل AI Packs به محصول قابل‌فروش
**نسخهٔ پیشنهادی: ۲۸ اکتبر ۲۰۲۶**

## اصل راهبردی

چهار مدل یا چهار Gateway، چهار محصول قابل‌فروش نمی‌سازند. مشتری برای کاهش هزینه، کم کردن ریسک یا افزایش درآمد پول می‌دهد—not برای تعداد endpointها. هدف اول باید یک مسئلهٔ تکرارشونده با کاربر مشخص و نتیجهٔ قابل‌اندازه‌گیری باشد.

## مرحلهٔ ۰ — کشف مشتری و انتخاب wedge (هفتهٔ ۱)

**مشتری هدف اولیه:** تیم‌های کوچک/متوسط محصول اجتماعی، دوستیابی و انجمن‌های دارای محتوای فارسی.

- با ۱۰ تا ۱۵ مدیر محصول، Trust & Safety یا CTO مصاحبه کنید.
- سه مشتری design partner بگیرید که نمونهٔ واقعی (با رضایت و حذف اطلاعات هویتی) و معیار موفقیت را تعریف کنند.
- هزینهٔ فعلی آن‌ها، تعداد موارد بررسی دستی، زمان پاسخ، false positive، false negative و خسارت اسپم/آزار را ثبت کنید.
- مسئله‌ای را انتخاب کنید که حداقل دو مشتری همین حالا برای حلش بودجه دارند.
- تا پایان مرحله، فقط یک ICP، یک job-to-be-done و یک معیار ROI داشته باشید.

**دروازهٔ تصمیم:** اگر مشتری حاضر نیست به اجرای پایلوت زمان، دادهٔ قانونی و ترجیحاً پول اختصاص دهد، به‌جای گسترش مدل‌ها محصول را کوچک‌تر یا مسئله را عوض کنید.

## مرحلهٔ ۱ — قرارداد محصول و بسته‌بندی (هفتهٔ ۱ تا ۳)

1. مسیر محصول را API-first/SaaS تعیین کنید؛ استفاده‌کننده لازم نیست Redis و مدل را در stack خود نصب کند.
2. OpenAPI یگانه و نسخه‌بندی‌شده بسازید؛ همهٔ پاسخ‌ها schema ثابت، request ID و error code قابل‌پیش‌بینی داشته باشند.
3. برای Python، TypeScript و PHP SDK رسمی تولید کنید؛ ابتدا سه SDK با test و مثال کامل بهتر از هشت SDK نیمه‌کاره است.
4. کلیدها را به tenant، محیط و پلن وابسته کنید؛ hash کلید در storage، revoke فوری، rotation، usage و quota مستقل.
5. secret مدیریت‌شده، TLS، حد اندازهٔ body، allowlist نوع فایل، timeout، محدودیت هم‌زمانی، backpressure و rate limit را اعمال کنید.
6. اگر Self-hosted لازم است، آن را یک توزیع مستقل با imageهای نسخه‌بندی‌شده و بدون مسیرهای بیرون از مخزن تعریف کنید.

**خروجی:** یک integration کارا، نصب‌شونده از صفر، همراه با API reference و نمونهٔ end-to-end.

## مرحلهٔ ۲ — کیفیت مدل و safety evaluation (هفتهٔ ۲ تا ۵)

برای Persian Trust & Safety API:

- مجموعهٔ آزمون برچسب‌خورده و مجاز با حداقل ۱٬۰۰۰ نمونه برای شروع بسازید؛ آن را بر اساس اسپم، توهین، آزار، تهدید، محتوای جنسی و false alarms تفکیک کنید.
- متن فارسی معیار، محاوره، فینگلیش، غلط تایپی و code-switching را پوشش دهید.
- به‌جای «دقت کلی»، precision، recall، false-positive rate، latency p50/p95 و عملکرد هر دسته را منتشر کنید.
- thresholdها را بر اساس سیاست مشتری تنظیم کنید؛ امتیاز مدل به‌تنهایی تصمیم قطعی نگیرد.
- صف بازبینی انسانی، feedback از تصمیم مدیر، appeal و تحلیل drift را اضافه کنید.
- هر به‌روزرسانی مدل را روی benchmark ثابت مقایسه کنید؛ رگرسیون کیفیت مانع release شود.

**دروازهٔ تصمیم:** پیش از فروش، باید بتوان به مشتری گفت مدل کجا خوب عمل می‌کند، کجا خطا دارد و در صورت ابهام چه اتفاقی می‌افتد.

## مرحلهٔ ۳ — قابلیت اتکا و عملیات (هفتهٔ ۳ تا ۶)

- CI برای تست unit، API contract، auth، quota، expiry، input limits و dependency failure.
- health/readiness واقعی؛ health نباید وقتی همهٔ سرویس‌ها down هستند healthy گزارش کند.
- HTTP client مشترک با timeout کنترل‌شده؛ پاسخ استاندارد برای 502/503/504 و trace/request ID.
- observability بدون ذخیرهٔ ناخواستهٔ متن شخصی: latency، تعداد خطا، مصرف مدل، queue depth و هزینهٔ per tenant.
- بارگذاری فایل با محدودیت حجم و streaming واقعاً تست‌شده؛ جلوگیری از پرشدن RAM.
- قفل نسخهٔ وابستگی‌ها، اسکن آسیب‌پذیری، SBOM، imageهای pin‌شده با digest و release notes.
- سیاست پشتیبان‌گیری، حذف داده، incident response و rollback.

**معیار پایلوت:** اهداف SLO ابتدا توافق شوند؛ نمونهٔ شروع ۹۹٫۵٪ دسترس‌پذیری ماهانه و p95 کمتر از ۵۰۰ ms برای moderation متنی سبک است. این‌ها هدف مهندسی‌اند، نه ادعای عملکرد فعلی؛ پس از benchmark باید بازنگری شوند.

## مرحلهٔ ۴ — طراحی بسته و قیمت (هفتهٔ ۵ تا ۸)

قیمت را از مقدار endpointها محاسبه نکنید. بر مبنای workload، هزینهٔ inference، ارزش بازبینی کمتر، سطح پشتیبانی و مسئولیت نگه‌داری بسازید.

| پلن آزمایشی | فرضیهٔ قیمت | مناسب برای |
|---|---:|---|
| Developer | رایگان با سقف پایین | نمونه‌سازی و ارزیابی، بدون SLA |
| Starter | ۱۹ تا ۲۹ دلار/ماه | محصول کوچک، quota محدود و dashboard پایه |
| Growth | ۷۹ تا ۱۹۹ دلار/ماه | تیم دارای usage بیشتر، policy rules، analytics و review workflow |
| Enterprise / private deployment | قیمت توافقی | الزامات حریم خصوصی، SSO، SLA، deployment خصوصی و پشتیبانی |

این اعداد **فرضیهٔ تست بازار** هستند، نه قیمت نهایی. از مشتری پایلوت دربارهٔ قیمت سؤال فرضی نپرسید؛ پیشنهاد واقعی با محدوده، سقف مصرف و شرایط روشن ارائه دهید.

## مرحلهٔ ۵ — تبدیل پایلوت به خرید (هفتهٔ ۶ تا ۱۲)

- مشتری قبل و بعد را بر اساس یک خط مبنا مقایسه کند: زمان رسیدگی، تعداد بررسی دستی، موارد از دست‌رفته، false positive و هزینهٔ عملیات.
- یک صفحهٔ live demo با ورودی نمونه و خروجی قابل توضیح بسازید؛ دادهٔ کاربران واقعی را در دمو استفاده نکنید.
- نمونهٔ integration برای WordPress و یک backend محبوب منتشر کنید؛ نصب، تست و حذف را مستند کنید.
- پایلوت را با معیار موفقیت ۲ تا ۴ هفته‌ای، سقف مصرف و جلسهٔ مرور شروع کنید.
- از سه design partner برای case study مجاز و قابل‌تأیید اجازه بگیرید.
- پس از اثبات conversion و margin، سراغ پک بعدی بروید.

## KPIهای هفتگی

- زمان تا اولین پاسخ موفق (time-to-first-value)
- نرخ موفقیت نصب از صفر
- درصد درخواست‌های 4xx/5xx و p95 latency
- کیفیت هر مدل نسبت به benchmark ثابت
- هزینهٔ واقعی هر ۱٬۰۰۰ عملیات و gross margin
- درصد مشتریان پایلوت که پس از دریافت نتیجه پول می‌پردازند
- تعداد false positiveهای گزارش‌شده و زمان رسیدگی
- درخواست‌های حذف داده و رعایت SLA حذف

## چه کارهایی فعلاً نکنیم

- قیمت قطعی برای چهار پک را بدون شواهد willingness-to-pay منتشر نکنید.
- Matching/Revenue را فقط با نام مدل‌های ML به‌عنوان ارزش تجاری عرضه نکنید.
- کلید مجوز را داخل JavaScript مرورگر یا اپ موبایل قرار ندهید.
- ادعای دقت، کاهش تقلب یا افزایش revenue بدون benchmark و مطالعهٔ کنترل‌شده مطرح نکنید.
- Self-hosted را «نصب با یک دستور» تبلیغ نکنید تا وقتی بسته از صفر، بدون مخزن اصلی، واقعاً ساخته و آزمایش نشده است.
